# How a GPU makes billions of Ed25519 keys per second

The naive way to search for a vanity address is a loop:

```
loop:
    seed   = 32 random bytes
    scalar = clamp(SHA-512(seed)[0..32])
    A      = scalar · B          ← ~250 point operations
    if address(A) matches: done
```

The scalar multiplication dominates completely. A good CPU implementation
manages perhaps 10⁷ addresses per second across all cores. Even a very large
GPU would only reach 10⁸ or so this way, because the work per candidate is
irreducibly large. To get to 10⁹ and beyond, the work per candidate has to
change, not just the number of workers.

Two observations do that.

## 1. Consecutive valid scalars differ by 8

Ed25519 *clamps* every secret scalar: it clears the low three bits, clears bit
255, and sets bit 254. Clearing the low three bits means:

> Every valid Ed25519 scalar is a multiple of 8.

So given any valid scalar `a` and its public point `A = a·B`, the sequence

```
a₀ = a       a₁ = a + 8      a₂ = a + 16     …     aₖ = a + 8k
A₀ = A       A₁ = A + 8B     A₂ = A₁ + 8B    …     Aₖ = Aₖ₋₁ + 8B
```

walks through valid scalars using **one point addition** per candidate instead
of a scalar multiplication. Since `8B` is a constant, it can be precomputed
into affine "niels" form and each step becomes a *mixed* addition: eight field
multiplications, against roughly two thousand for a scalar multiplication.

That is a ~250× reduction in work per candidate, and it is the entire reason
this is feasible. The technique comes from `mkp224o`, the established CPU
vanity generator.

Implemented as `ge_add_8b` in [`cuda/ge25519.cuh`](../cuda/ge25519.cuh), with
the constant generated by [`cuda/gen_constants.py`](../cuda/gen_constants.py)
and pinned against `curve25519-dalek` in the tests.

### What this costs you: no seed

The scalar you land on is `a + 8k`. There is no seed that produces it, because
SHA-512 cannot be inverted. So the output must be an *expanded* key — the
64-byte `(scalar ‖ nonce)` form — rather than a 32-byte seed.

This costs nothing in practice: Tor's `hs_ed25519_secret_key` file stores
exactly that expanded form and never wants a seed. It does mean `honion` output
cannot be fed to tools that insist on seeds.

And since the seed relationship is broken anyway, `honion` skips SHA-512
entirely and draws the clamped scalar straight from the system CSPRNG. A
clamped random draw is uniform over precisely the same set of scalars that
hashing-then-clamping a random seed would produce. See
[05-security-model.md](05-security-model.md).

### The invariant that has to be checked

Clamping puts every scalar in `[2^254, 2^255)`. Adding `8k` could in principle
carry past `2^255` and leave the valid set. With `k` bounded by 2³², the step is
at most 2³⁵, so this requires a starting scalar within 2³⁵ of the top of a
2²⁵⁴-wide range — a probability around 2⁻²¹⁹.

`SecretScalar::offset` checks it anyway, and returns an error rather than a
key. "Astronomically unlikely" is a reason to expect the check to never fire,
not a reason to omit it.

## 2. The dual addition law: two candidates for the price of one

The obvious way to use observation 1 is to step a single point forward, once per
candidate, in extended coordinates `(X:Y:Z:T)`:

```
ge_madd        P + 8B, giving a p1p1        4 multiplications
ge_p1p1_to_p3  back to extended coordinates 4 multiplications
```

Eight multiplications per candidate, four of which exist only to convert a
result back into the form the *next* addition needs. That is pure overhead: the
search never wants a point, it wants a `y` coordinate.

For a twisted Edwards curve with `a = -1` there is a better formula. The **dual
addition law** gives `y` directly, as a fraction, with no reference to the curve
constant `d` and no projective coordinates for the result:

```
y(P + Q) = (x₁y₁ - x₂y₂) / (x₁y₂ - y₁x₂)
y(P - Q) = (x₁y₁ + x₂y₂) / (x₁y₂ + y₁x₂)
```

Look at what the two share. Both need `x₁y₂` and `y₁x₂`, and they differ only in
whether those are subtracted or added. `x₁y₁` belongs to the moving point and is
computed once per batch; `x₂y₂` belongs to a *fixed* offset and is precomputed.

So **two multiplications produce two candidates** — `P+Q` and `P−Q` — where the
extended-coordinate walk needed eight for one.

(The law is verified against the standard addition law over random point pairs
by [`cuda/verify_dual_law.py`](../cuda/verify_dual_law.py), which was run before
any of it was written in CUDA.)

### The shape this forces

The formula takes a *fixed* offset `Q`, so the kernel keeps a table of them:
`8B, 2·8B, …, HALF·8B`, precomputed in affine form with `x·y` alongside. Each
batch then:

1. takes the current base point `P` in affine form,
2. emits `2 × HALF` candidates as `P ± j·8B`, plus `P` itself,
3. advances `P` by the giant step `(2·HALF + 1)·8B`.

Successive batches tile the integers exactly — the range `[-HALF, +HALF]` around
each base point, stepping by `2·HALF+1` — so no key is examined twice and none
is skipped. A thread starting at scalar `a₀` therefore covers a contiguous run
of `a₀ + 8m` with **`m` signed**, which is why a reported match may lie *below*
where its thread started.

## 3. The affine coordinate is the real cost, so inversions are batched

Points are held in extended projective coordinates `(X:Y:Z:T)`, where
`x = X/Z` and `y = Y/Z`. That is what makes addition inversion-free. But an
address needs the *affine* `y`, and recovering it means a modular inversion —
about 265 field multiplications, or thirty times the cost of the addition that
produced the point.

Doing that per candidate would throw away everything observation 1 won.

**Montgomery's trick** inverts `n` values with a single inversion. Build the
running products, invert only the last one, then walk backwards: at each step
the accumulator holds the inverse of everything up to that point, so multiplying
by the previous running product isolates one inverse, and multiplying by the
value itself moves the accumulator down.

Because the dual law already produces each candidate as a numerator over a
denominator, the numerators can be folded into the *forward* pass — each is
multiplied by the running product of all denominators before it. The backward
pass then recovers `y` in two multiplications instead of three, and the division
implied by the formula costs nothing at all.

One further economy: the base point's own `Z` is folded into the same product,
so a batch needs exactly **one** inversion — not one for the candidates and
another to make the next base point affine.

### A small optimisation that pays twice


The compressed public key is the affine `y` with the low bit of the affine `x`
placed in bit 255. Bit 255 is base32 character 51 — past every prefix that can
be searched (see [00-onion-v3-address-spec.md](00-onion-v3-address-spec.md)).

So `honion` never computes the affine `x` at all. That saves a multiplication
per candidate, and — more importantly — lets the forward pass store two field
elements per candidate instead of three, which is a third off the local memory
that limits occupancy.

## Adding it up

Per candidate, with `HALF = 256` (so 513 candidates per batch):

| step | field multiplications |
|---|---|
| `x₁y₂` and `y₁x₂`, **shared between `P+Q` and `P−Q`** | 2 per *two* candidates → 1 |
| Montgomery forward fold (numerator, running product) | 2 |
| Montgomery backward pass | 2 |
| amortised inversion (~265 / 513) | ~0.5 |
| **total** | **~5.5** |

The straightforward extended-coordinate walk costs twelve. Measured throughput
on an RTX PRO 6000 Blackwell went from 4.9 × 10⁹ to 8.4 × 10⁹ addresses per
second when the kernel was changed from one to the other — a 1.7× improvement
that is entirely explained by this table. See
[06-performance.md](06-performance.md) and
[07-benchmarks.md](07-benchmarks.md).

### What it costs

Per-thread memory. Each candidate's numerator and denominator must be held until
the batch inversion completes: two field elements, 80 bytes, times `2 × HALF`.
At `HALF = 256` that is 41 KB per thread. The extended-coordinate walk needed
three field elements per candidate but far fewer candidates in flight.

There is also a table of `HALF` precomputed offsets in shared memory — 30 KB at
`HALF = 256` — which is why the offset loop reads from `__shared__` rather than
re-reading global memory two hundred times per batch.

## Why the GPU is never trusted

The device is given public points and integer tables. It returns
`(thread, iteration)` pairs. The host reconstructs the secret as
`a₀[thread] + 8·iteration` from its own memory — the device never holds, sees,
or returns secret material.

This is not only a security property; it is what makes the performance work
safely. Everything above is an optimisation, and optimisations have bugs. Since
every reported candidate is rebuilt and re-verified on the CPU with an
independent implementation before anything is written, a bug in any of it costs
time and cannot produce a bad key. See
[05-security-model.md](05-security-model.md).
