# The kernel: how the search actually runs on the GPU

Read [01-ed25519-vanity-search.md](01-ed25519-vanity-search.md) first for *why*
the algorithm looks like this. This file is about how it is built.

## Layers

```
cuda/fe25519.cuh    arithmetic in GF(2^255 - 19)
cuda/ge25519.cuh    Edwards curve points, the +8B step, decompression
cuda/search.cu      the search loop and the pattern prefilter
```

Each layer is verified against an independent implementation before the layer
above it is trusted:

| layer | checked against | test |
|---|---|---|
| field (both implementations) | `num-bigint` modular arithmetic | `tests/field_arithmetic.rs` |
| group | `curve25519-dalek` | `tests/group_arithmetic.rs` |
| search | the host reference matcher in `honion-core` | `tests/search_kernel.rs` |

This ordering is the point. A vanity search that is subtly wrong does not
crash — it runs at full speed and finds nothing, which is indistinguishable
from bad luck. The only defence is to establish correctness bottom-up, against
implementations that share no code with ours.

## Field arithmetic: two implementations, one interface

`cuda/fe25519_u32.cuh` is what the search kernel uses. `cuda/fe25519.cuh` is the
implementation it replaced, kept because it is an independent second opinion:
`crates/honion-gpu/tests/field_arithmetic.rs` runs the same differential suite
against both, so a mistake in the fast one has to be a mistake that also fools
`num-bigint`.

### What it uses now: eight 32-bit limbs

```
h = h[0] + h[1]*2^32 + h[2]*2^64 + ... + h[7]*2^224
```

Saturated limbs, carries propagated with the hardware carry flag via
`mad.lo.cc.u32` / `madc.hi.cc.u32` chains. The multiply is schoolbook 8x8: two
carry chains per row — one for the low halves of that row's products, one for
the high halves shifted a limb up — at 18 instructions per row, 144 for the full
512-bit product, then about 40 more to reduce it with `2^256 = 38 (mod p)`.

Each row is a **single** inline-asm block. That is not stylistic: a carry chain
must not be split across statements, because the compiler may schedule other
instructions between them and the carry flag would not survive.

The multiply is generated by `cuda/gen_fe32.py` rather than hand-written. It is
144 lines whose only content is operand indices, and a transposed index there is
invisible to review and fatal in effect. The two functions in that file that
*were* hand-written, `fe_add` and `fe_sub`, both shipped with exactly that bug —
numbered as though there were eight outputs when there are nine — and the
differential test caught them on the first run.

### What it replaced: radix 25.5

Ten signed limbs alternating 26 and 25 bits, accumulated into 64-bit registers,
following the Ed25519 reference implementation. Carries are deferred rather than
propagated, which makes addition and subtraction ten plain integer operations
and makes the whole thing much easier to get right.

It was the right way to start and the wrong way to finish. Profiling the search
kernel showed **56% of its PTX operations were 64-bit** — 1606 `add.s64`, 1232
`mad.lo.s64`, 327 `shr.s64` — and each of those is two 32-bit operations on this
hardware. The kernel was spending most of its time synthesising arithmetic the
machine does not have. After the switch, 64-bit operations are **2%**, and
throughput went from 8.3 to 11.3 × 10⁹ addresses per second.

### The trade

Addition and subtraction got *more* expensive: they now need a real carry chain
and a fold where before they could just add limbs and defer. The search kernel
does about five multiplications and two additions per candidate, so the multiply
dominates and the trade pays. On a kernel with a different mix it might not.

### One thing that did not change

`fe_tobytes` is still total — it accepts any limb values the other routines can
produce and canonicalises them itself, rather than documenting a precondition
callers must remember. The reference implementation this all started from does
the latter, and violating it yields an answer wrong by exactly 19: plausible
enough to survive inspection. A contract that cannot be violated is worth a few
instructions.

## The search loop

Per thread, per batch. `HALF` is the number of precomputed offsets; a batch
covers `2·HALF + 1` candidates.

```
setup (once):  offset table = affine (x, y, x·y) of 1·8B … HALF·8B,
               plus the giant step (2·HALF+1)·8B in niels form

per batch:
  check       the base point itself (its y is already affine)
  forward     for j in 0..HALF:
                  two multiplications give P ± (j+1)·8B as fractions
                  fold each numerator into a running product of denominators
                  -- two independent products, one for +, one for -
  advance     P += giant step, and fold its Z into the same product
  invert      ONE fe_invert for the whole batch, covering both chains and Z
  backward    for j in HALF-1 .. 0:
                  rebuild that pair's two denominators from the offset table
                  y = acc · numerator;  acc ·= denominator   (both chains)
                  test each y against the pattern tables
```

Two details in there are the result of profiling, and both look wasteful until
you see the measurements.

### Denominators are recomputed, not stored

The forward pass could store each candidate's denominator for the backward pass
to read back. It does not; the backward pass rebuilds it with two extra
multiplications per pair.

That is more arithmetic and less memory, which is the right way round here. With
both halves of each fraction stored, the kernel moved about 106 bytes per
candidate and DRAM sat at **61% of peak** — while ablating a fifth of the field
multiplications changed throughput by **0.13%**. The kernel was bound by memory
bandwidth and had arithmetic to spare. Dropping the stored denominators halved
the traffic (1.05 TB/s → 577 GB/s) and took throughput from 10.9 to 12.5 × 10⁹
addresses per second.

### The running product is split in two

A single running product is a dependency chain `2·HALF` multiplications long,
and each link is a full `fe_mul`. Splitting it into one accumulator for the `+`
candidates and one for the `-` candidates halves the critical path and gives the
scheduler two independent streams per thread. They are recombined at the end of
the batch for a dozen multiplications, against a thousand candidates.

Worth 12.5 → 13.3 × 10⁹ addresses per second.

## What did not work

Recorded because the failures locate the ceiling more precisely than the
successes do, and because each cost real time to establish.

| attempt | result | why |
|---|---|---|
| **Four accumulator chains** | 12.1 vs 12.9 G/s | 224 registers instead of 128, so one block per SM instead of two. Occupancy fell 30.7% → 16.7% and the extra parallelism did not pay for it. |
| **`__launch_bounds__(256, 3)`** | 11.5 vs 12.9 G/s | Forcing the compiler to 85 registers spills more than the extra warps recover. |
| **Unrolling the offset loop** | slightly slower at ×2 and ×4 | There is one hardware carry flag, so carry chains cannot interleave no matter how much instruction-level parallelism is exposed. |
| **Skipping unused numerators in the backward pass** | no change | Genuinely less work — two field additions and a third of the table read per pair — and worth exactly nothing, because the kernel is latency-bound. |
| **Staging the offset table in shared memory** | no change, costs 30 KB/block | Warp-uniform reads are broadcast from L1 anyway. |

The common thread: after the memory fix, removing *work* stopped helping. What
matters is latency and how much of it can be hidden.

## Where the ceiling is

| | value |
|---|---|
| registers per thread | 128 |
| blocks resident per SM | 2 |
| achieved occupancy | 30.7% |
| instruction issue rate | 0.58 / cycle / scheduler |
| busiest pipe (ALU) | 32% |
| DRAM | 34% of peak |

Nothing is saturated. The kernel is waiting, and there are only two warps per
scheduler to wait with. Occupancy is quantised: three blocks per SM needs **≤85
registers**, and `fe_mul` alone holds 26 words of temporaries before the live
base point, accumulators and outputs are counted. Getting there is not a tuning
change, it is a different kernel.

## The prefilter## The prefilter

A pattern compiles to a 64-bit `(mask, target)` pair over the first eight key
bytes read big-endian. A candidate passes when `key & mask == target`.

`8 bytes = 64 bits = 12.8 base32 characters`, and a 12-character prefix takes
about 36 years at 10⁹/s — so the prefilter covers every pattern that can
actually be searched to completion, and the hot loop is one masked compare.

Patterns are grouped by identical mask; each group's targets are sorted, so the
device does one mask and one binary search per group. Searching ten thousand
patterns of the same shape costs barely more than searching one.

Constraints the 64-bit prefilter cannot express — multi-character classes, and
positions past character 12 — become *residuals*, checked only on candidates
that already passed. For most patterns there are none.

A pattern whose prefilter is too weak would forward candidates faster than the
host can verify them. `DeviceTables::check_selectivity` refuses those up front
with an explanation, rather than letting throughput mysteriously collapse.

## Two things the compiler had to be told

**Cold routines are `__noinline__`.** `fe_invert` and `fe_pow22523` expand to
261 field operations each, themselves hundred-term multiplications. Inlining
them multiplied the PTX by roughly fifty. They run once per batch, so a real
call costs nothing and keeps the hot loop in the instruction cache.

**Batch loops are `#pragma unroll 1`.** Left alone, NVRTC's unrolling heuristic
flipped unpredictably with the batch size:

| batch size | compile time | PTX | throughput |
|---|---|---|---|
| 32 | 44 ms | 4.9 MB | 0.99 G/s |
| 64 | **284 s** | 9.6 MB | — |
| 128 | 11 ms | 876 KB | 4.35 G/s |

The compact code was four times faster, and the cliff at 64 made the build
unusable. Pinning unrolling off gives predictable size and compile time at every
setting, and made throughput monotonic in the batch size as the arithmetic says
it should be. Unrolling the offset loop by two was tried again after the
dual-law rewrite and measured slightly *slower*, so it stays off.

## Why NVRTC instead of nvcc

`nvcc` cannot run on this machine at all. CUDA 13.1's `crt/math_functions.h`
declares `rsqrt`/`rsqrtf` without exception specifications; glibc 2.42 declares
the same C23 functions `noexcept(true)`, and the conflict is a hard error —
including for `--ptx` and `--cubin`, which need no host compiler. Changing
`-ccbin` does not help, because the glibc headers are the same either way.

NVRTC compiles device code in process and never includes a host header, so the
conflict cannot arise. Three things follow, all of them improvements:

- The build needs no CUDA toolkit, only the driver and `libnvrtc` at run time.
- The target architecture comes from the GPU actually present, not a build-time
  guess.
- Per-run constants — `BATCH_SIZE` — are compiled *into* the kernel.

Compilation takes about 2.9 s and module loading about 100 ms, once per run.

`include` directives are resolved by `honion-gpu`'s own expander against a
closed list of embedded headers, because NVRTC does not apply `#pragma once`
across buffers pasted together. The set of text that can reach the device
compiler is fixed at build time; sources are embedded with `include_str!`, so a
binary carries the exact kernel it was built with.
